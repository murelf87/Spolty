- Spotly frontend uses a single mobile-first shell with state-driven primary tabs, because the reference defines app navigation rather than separate shareable content pages.
- Spotly brand colors and effects live in `src/styles.css`; feature components use semantic token utilities only, so visual identity remains consistent.
- Spotly's primary production targets are native iPhone and Android apps packaged with Capacitor, followed by an installable web app; user data remains in the shared cloud backend so all three clients interoperate.
- Lovable Cloud handles Apple/Google/email sign-in and, since the owner asked for production, the social core (Spots, voices, follows, chats, stories, saved, blocks, reports); features without a backend yet (payments, live audio, business tools) stay visibly demo-only.
- The host live-broadcast experience is a separate stateful frontend flow opened from Create Spot, with topic, voice-first format, area, audience, moderated voice requests, room settings, camera, microphone, timer and ending summary; all are visibly demo-only because streaming and persistence are intentionally out of scope.
- Spot publication keeps discovery topic, approximate area, audience and voice-reply controls in its review step, because an audio-first social post needs discoverability and conversation settings before sharing.

- Verification remains a self-contained illustrative frontend flow without document capture, biometric processing, or account status mutation until an identity provider is selected, because sign-in proves account ownership, not legal identity.
- The Audio Wall discovery screen stays separate from private voice chats, and its room joining is labeled demo-only because live audio transport is not yet implemented.
- Spotly is voice-only: users write nothing except titles (Spot title, names); descriptions, comments, replies, chats and the profile presentation are voice, because the owner set this as the product's core rule.
- All voices share the owner's voice-reply design, reproduced pixel by pixel from the owner's image (measurements and colours in the `--voice-*`/`--wave-*` tokens of `src/styles.css`), and one engine: `VoiceThread.tsx` (VoiceRow/VoiceItem: ring avatar, play, real waveform in 3 px bars with silences as dots, played part fuchsia-to-violet up to a pink playhead, current and total time under the wave, like and a speaker with the number of replies (it plays them in a row; the design's chat bubble was replaced by a speaker because Spotly has no written chat bubbles), share and options centred, and «↳ En respuesta a este audio» (or «En respuesta a <name>» for a reply to a reply) on every reply; no name line, as in the design; VoiceComposer opens already recording: photo, «Respondiendo a» and the minute of the original | stop · live wave · time · send, gradient border and a notch that rises to the photo of the audio it answers, with no «×» while recording; VoiceThread with chained replies via `parentId`), `lib/voice/recorder.ts` (real MediaRecorder + live levels, preview, discard, explicit send, < 0.8 s ignored), `lib/voice/player.ts` (one audio at a time, stopped on navigation) and `lib/voice/notes.ts`. Replies are «mensajes de voz», never «comentarios»: a Spot's or photo's messages show the original audio first (with its likes, speaker and share), a gradient «Responder con tu voz» button opens the composer attached under it (replying to a specific voice is in its ⋮ menu), and there is no text-box bar or speech-bubble icon anywhere; the same pieces are used in photos, Hot Spots, group chats (1:1 chats keep the neon bubbles but use the same composer), communities, events, businesses and the profile wall. The microphone icon only means recording; listening uses play or a speaker (`Volume2`).
- The cloud layer (`src/lib/cloud`) is used only when signed in, the migration `supabase/migrations/20261008140000_spotly_social.sql` is applied and demo mode is off; otherwise voices and Spots persist on the device in IndexedDB (`lib/voice/notes.ts`, `lib/spots.ts`) behind the same interface, and the preview and PWA builds set `VITE_SPOTLY_CLOUD=off` so they never call the server. RLS, masked anonymous authors (`*_public` views), storage path rules and rate limits are covered by `supabase/tests` (SQL, API against PostgREST 14 and a two-person browser E2E).
- Fabricated numbers (sample likes, replies, shares, views, KPIs, badges) only appear in demo mode («Saltar todo», `store.demo`); with a real account sample content has no audio, is labelled «ejemplo» and only counts the user's own actions, so nothing looks like traction that does not exist.
- Home is a full-screen feed: every Spot (and every sponsored/Hot Spot insert) is one snap page exactly between the sticky header and the bottom nav, because cards ending at different heights was rejected by the owner.
- The bottom navigation icons each use their own brand gradient (cyan, blue, violet, fuchsia) and «En línea» is always green (`--online`); the centre create button keeps its approved neon style.
- The profile has a changeable cover (own photo or Spotly backgrounds), the avatar overlapping it at the left, a voice presentation instead of a written bio, and tappable Spots (with views), Followers and Following lists, to avoid an Instagram-like layout.
- The artifact preview (`preview.html`) is a separate single-file build (`npx vite build -c vite.preview.config.ts`, sources in `preview/`): `<body>` acts as the iPhone screen so `fixed` overlays stay inside it, and `preview/phone-css.ts` evaluates media queries at 390 px and maps vh and safe-area insets to the simulated phone, so app components keep plain production code with no preview-only branches.
- The phone-test PWA is a separate demo build without backend (`npx vite build -c vite.mobile.config.ts`, sources in `mobile/`) published only as build output on the `gh-pages` branch (GitHub Pages: https://murelf87.github.io/Spolty/), together with `expo/App.js` to open it inside Expo Go; `main` stays the Lovable-synced source.
- Profile, author and photo-wall thumbnails always open something: photos and videos use the sample registry `src/lib/media.ts` (short demo clips in `src/assets/videos` made from the sample photos) and the shared `MediaViewer`, until the social backend provides real media.
- Every phone gets the same proportions: on viewports up to 480 px the root font size is fluid (16 px at 390 px, clamped 14–17.5 px) and all component sizes are rem (named small text sizes `text-2xs/3xs/4xs`, lucide icon sizes mapped to rem in `src/styles.css`), so no fixed px sizes except hairlines, borders, shadows and desktop widths.
- Screens share one structure from `kit.tsx`: `TopBar` (top spacing from `--safe-header`) for every header, `BottomSheet` for every sheet, and the default `Button` as the brand gradient pill (buttons with their own background add `bg-none`), because consistency across screens was an explicit request.
- Poppins is bundled in `src/assets/fonts/poppins` (OFL) instead of Google Fonts, so iPhone, Android, the PWA, the preview and Capacitor render the same typography offline and without third-party requests.
- Communities and events are real and shared in the cloud (`communities`, `community_members`, `events` with a voice flyer, `event_attendees`; conversations in the `group:<id>` and `event:<id>` voice threads); without cloud they keep the sample ones (numbers only in demo) and what you create is stored on the device (`lib/gatherings.ts`). Their topics are the Spot topics, so a community's Spots tab shows Spots of its topic.
- Notifications are derived from real data (`fetchActivity`: new followers, voices on your Spots and wall, notes in your chats) with a «seen» mark per account; the bell dot only shows when there is something new, and sample notifications exist only in demo mode.
- Settings only offer what works (theme saved on the device, privacy facts and links, data download, account deletion); push notifications arrive with the App Store and Google Play apps, and the onboarding asks the real system permissions and detects the province from GPS (`provinceAt`).
- Every audio shows its author's photo (and the name wherever the layout has a name: Spot header, profile, chat, the voice options sheet and the accessible label); only paid Incógnito (granted server-side) turns it into a ghost labelled «Anónimo» (`SignAs`, `AnonAvatar`, anonymous `VoiceItem`), and the user's profile (name, user, cropped 512 px photo, cover) lives in the store, persisted to localStorage and synced to the cloud `profiles` row when signed in.
- The native iPhone and Android apps package the production app as a static bundle (`vite.app.config.ts`, sources in `app/`, cloud on, Supabase URL and publishable key from the environment) in `dist-app`, which `capacitor.config.ts` uses (`CAP_SERVER_URL` only for live reload), because store builds must not depend on a Lovable preview URL; inside the native app Apple/Google sign-in explains that email is used until deep links are configured (`docs/APPS_NATIVAS.md`).
- Activating the cloud is a documented manual step (`docs/ACTIVAR_NUBE.md`: Lovable's SQL editor or its chat), because a migration committed from outside Lovable is not guaranteed to run on Lovable Cloud; Settings states whether data is in the cloud or only on the device.
- The Home location button opens «Tu zona» (the shared `PlaceBrowser`), and the chosen town feeds «Cerca», the map and Create Spot, because the area must be the user's real one rather than a fixed sample city.
- Claims about people being «verificadas» are avoided outside illustrative flows, because sign-in only confirms the account (Apple, Google or a confirmed email), not identity.
- With the cloud on, the Explore map places the chosen town's recent real Spots in fixed radar slots around the user's photo and says positions are approximate, because Spots store only a town or zone, never coordinates; sample pins only appear without the cloud.
